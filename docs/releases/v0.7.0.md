# Flame 0.7.0 Release Notes

Status: prepared, not published. No tag, crate, wheel or image for `v0.7.0` exists yet.

Release branch: `release-0.7`. `v0.7.0` is a tag on this branch; the source commit is recorded when the tag is created.
Previous release: `v0.6.0`. Previous release candidate: `v0.7.0-rc3`.

This is the stable release of the 0.7 series. Its content is `v0.7.0-rc3` plus the release-tooling fix below. The notes of the candidates describe the changes in detail and all still apply:

- `docs/releases/v0.7.0-rc1.md`: everything merged to `main` between the 0.6 notes and the `release-0.7` branch point (70 changes, #493 to #609).
- `docs/releases/v0.7.0-rc2.md`: eight changes backported after rc1, and the release tooling fixes.
- `docs/releases/v0.7.0-rc3.md`: the three changes backported after rc2.

## Release history of the candidates

`v0.7.0-rc1` and `v0.7.0-rc2` were tagged, but their publish runs failed before the `flamepy` wheel and the crates went out, so rc3 is the first candidate that PyPI and crates.io carry.

- `v0.7.0-rc1`: `Release Metadata` failed (the `flamepy` version was compared with color codes). Nothing was published.
- `v0.7.0-rc2`: the images were published; `Publish flamepy` failed in its installed-package check, and `Publish Rust crates` failed with a crates.io 403.
- `v0.7.0-rc3`: `stdng 0.1.9`, `flame-rs-macros 0.7.0-rc3`, `flame-rs 0.7.0-rc3`, the images and `flamepy 0.7.0rc3` are published. Its publish run still ended red, at the post-upload check of PyPI (see below).

## Changes since rc3

- **`verify-pypi` bypasses uv's cached package index (#653, backport #654).** After `flamepy 0.7.0rc3` was uploaded, the workflow's check retried 30 times and reported the version as missing, which turned the run red although the package was on PyPI. The most likely cause is that uv reused a cached package index from before the upload; the install now passes `--refresh`. This is release tooling only; the packages are unchanged.

## Upgrade Notes

- Everything in the rc1, rc2 and rc3 notes applies, in particular:
  - the `flamepy.agent` and `flamepy.app` replacements of the old Runner and tools APIs (rc1, rc2);
  - the executor attribute change, which requires the session manager, the executor manager and the SDKs to be upgraded together (rc2);
  - the rule that a gang's `min_instances` is 0 or its size (rc2);
  - that sessions without affinity rotate across executors instead of always going to the smallest executor ID under `das` (rc3).
- The Helm chart `appVersion` and image tags move to `0.7.0`.

## Known Gaps

- The release sanity checks that need the registries, Docker or Kubernetes were not run as part of preparing this change.
- `stdng 0.1.9`, `flame-rs-macros` and `flame-rs` `0.7.0-rc3` are on crates.io; the stable crates `0.7.0` are not, and a failed upload of a crate cannot be redone under the same version, so check the credentials before tagging.
- The stale-cache case behind #653 can only be confirmed by a real upload.

## Before tagging

- #654 must be merged into `release-0.7` (the publish workflow runs `hack/release.sh` from the tagged commit).
- Confirm `PYPI_API_TOKEN`, `CARGO_REGISTRY_TOKEN` and `DOCKER_HUB_PAT` are still valid; rc3 exercised all three.
- Confirm CI is green for the final commit. For the rc3 commit (`8121d338`) Kubernetes E2E, the Python and Rust E2E and system tests on `priority` and `drf`, and the shim E2E and benchmarks passed; only `Publish flamepy` was red.
- Tag `v0.7.0` on `release-0.7` and omit `--prerelease` when creating the GitHub release.
